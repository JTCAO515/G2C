# CJ006 journey-needs container

Scope follows original [CJ013 / Issue14](https://github.com/JTCAO515/G2C/issues/14) and docs/ui.md: a lightweight view/correction entry in the existing Assistant flow, with no new tab, extraction, planner, Memory or formal Trip writes. Issue14 was read through the official GitHub connector using stable repository ID1428033587 after the old repository URL redirected. Its historical planning wording does not override Main's current authorized implementation scope; original I/device/real user-flow acceptance remains open.

The Assistant's existing sheet router now offers Journey needs alongside its existing recovery/history controls. Account/my settings stay in Memory; brand/floating controls/composer/resources are preserved. The screen presents canonical current details and revision fields with source kind, original revision statement and version. Corrections are behind an optional DisclosureGroup, using public NeedsDetailsView and NeedsEditorView in English/Chinese. Unknown dates/budget and unedited fields remain unfilled; money/date/time representations are domain-owned. User-provided fixed/booked items are explicitly not supplier-verified orders.

## Trusted composition and lifecycle

The root supplies NeedsContainerHost to the existing ShellView and binds an actual NeedsClient, NeedsBinding, existing selectedNeedsID, original SessionLifecycle/SessionOperation, ShellGeneration and the same current-binding callback as the client. No default needs/trip/account/environment ID, endpoint, key/store, source statement, authority or model extraction is fabricated. Init/bind/language/foreground do not fetch or create data. Missing trusted selection is unavailable, and a missing server record does not automatically create a version-zero draft.

Each binding installs a distinct canonical NeedsPresentation. Original UI context is checked before synchronously calling prepareDetail, prepareRevision or prepareQuery; only the resulting opaque NeedsPresentationWork is placed in a Task. Host identity/session/epoch and domain one-use work checks wrap execution. Duplicate work cannot release busy or send twice. Direct revision input accepts a positive integer only and always uses the root's selected needsID. Recovery only exposes and queries canonical pending records for that exact needsID; it cannot retarget another journey's pending record.

Local editing captures a private editing revision before the trusted binding callback and checks it again afterward, in addition to original host context, editorID, needsID and expectedVersion. Only an accepted local edit rotates this token; a rejected edit does not. This preserves newer same-editor edits, including edit-away-and-back callbacks, without changing server expectedVersion or invalidating ordinary consecutive editing. Loading latest preserves existing draft and expected version; it does not silently rebase, auto-retry CAS or overwrite edits. No action ID is generated and no save work is prepared by this container. Save is explicitly disabled regardless of read availability. A future write/collection-policy integration requires separate authorization and the canonical capability; this UI is not a write switch.

Account/environment/selection changes must invalidate before installing new trusted inputs. Own private host references are cleared before canonical old-model invalidation. ShellState invokes NEEDS cleanup before the existing Trip/Memory/history/message cleanup and rechecks generation between them. Inactive/background removes private snapshot/revision/receipt/draft/pending state; there is no foreground rebind. The per-binding view identity also resets revision input. Language changes preserve the same current model/draft.

Original action results are confirmed only through canonical receipt plus exact historical revision/original-byte reconciliation. Null/malformed/cancellation stays unknown and never means resend permission. A latest detail read is shown separately and never substituted for receipt proof. Missing store/key fails visibly; no key creation, plaintext fallback, silent empty success or storage cleanup is introduced.

Source, intercepted local tests and unsigned module compilation do not prove a trusted live composition root, system extraction, real save, App rendering, VoiceOver or full Issue14 acceptance.
