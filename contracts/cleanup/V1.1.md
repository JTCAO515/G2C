# CLEANUP@1.1

Frozen additive version for C's #402 Unicode item-ID gap. All [CLEANUP@1.0](V1.md)
authority, locking, exact original request/result, selection and erasure semantics
are retained. V1 bytes and acceptance remain unchanged; there is no implicit upgrade
or downgrade. Only the following version-specific differences apply:

- Protocol is exactly `CLEANUP@1.1` in requests, receipts and the registry's
  `cleanup_protocol` marker. A 1.0 decoder rejects 1.1 and vice versa.
- `selection.item_id` for `kind=memory` follows the current MEMORY identifier:
  a nonempty, non-whitespace-only Unicode string of at most **4096 characters**.
  Preserve exact spelling, leading/trailing characters and UTF8 bytes. No Unicode
  normalization, trimming or case folding. Invalid Unicode scalars and NUL are
  rejected at the PostgreSQL text/UTF8 boundary. Operation/invocation/target IDs
  keep their original ASCII grammar and bounds.
- Request bound is **131072 bytes**, enough for maximum valid MEMORY ID and domain
  scope under both literal UTF8 and JSON ASCII escapes. Receipt bound is still
  4096 bytes. Canonical request digest still hashes the exact original bytes,
  including whitespace and escape spelling.

Python: `cj_cleanup.hooks_v1_1` exports `Selection`, `HookRequest`, `HookReceipt`,
`make_request`, `make_receipt`; the execute/reconcile ABI is unchanged. Hosts must
explicitly choose the codec matching the frozen target entry. Wrong-version receipts
never count as confirmation. #402's local Store/Coordinator will expose explicit
codec selection when delivered; the old internal rc remains closed and unchanged.

Positive examples and executable controls are in `backend/cleanup/tests/test_hooks_v1_1.py`:
Chinese/emoji, combining/precomposed distinct IDs, a maximum 4096-character ID,
both literal UTF8 and ASCII-escaped requests larger than 16KiB. Negative examples:
4097 characters, empty/whitespace, NUL/surrogate, changed original bytes, wrong
protocol, receipt downgrade and attempts to put Unicode in operation IDs.

This version grants no new deletion authority or Memory write. C still resolves
the exact item/version/withdrawal under its own canonical lock and supplies its
actual domain hook; B does not infer item associations or implement C's hook.
