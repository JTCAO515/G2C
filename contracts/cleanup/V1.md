# CLEANUP@1.0

Frozen 2026-11-02 for #402 / #26 / #27. This additive domain-hook contract does
not change `CJ-CLEANUP-INTERNAL@0.1.0-rc.1` or progress-read rc semantics.
It authorizes neither a client request nor an external/production deletion.

## Authority and registration

The trusted coordinator binds the fresh canonical AUTH principal and explicit
environment to the domain's canonical `domain_scope`. Never accept a request's
owner, scope, registry, hook, SQL, module name or filesystem path as authority.
`subject_digest` is SHA256 of the existing canonical cleanup Scope encoding
(`core.encode(asdict(scope))`); it binds the operation across domain scopes.
Digests are correlation metadata, not bearer credentials or confirmation proof.

Each **provided private storage object** registers its tables/files, owner line,
retention category, restore fence and explicit injected hook in the same PR that
provides it. `cleanup_protocol: "CLEANUP@1.0"` means its owner implemented and
tested that hook; merely documenting this protocol must not set that field.
The coordinator compares an independent host inventory with the registry, freezes
the complete bytes and each target entry, and requires a matching injected hook.
Missing/changed/new entries latch `blocked`; no silent omission, enlargement or
shrinking of the confirmed scope. Existing not-provisioned placeholders are not
evidence of erased storage. No JT Agent placeholder is added.

## Hook ABI

`cj_cleanup.hooks` supplies immutable `HookRequest`, `HookReceipt`, `Selection`
and structural `DomainHook`. Explicit server composition injects each domain hook:

```python
class DomainHook(Protocol):
    def execute(self, request: HookRequest) -> HookReceipt: ...
    def reconcile(self, request: HookRequest) -> HookReceipt: ...
```

The coordinator durably commits the **exact request bytes** as intent before
`execute`. `reconcile` only queries the original invocation; it cannot execute,
retry, mint an ID or reinterpret absence as permission to run. Owner implementations
persist original invocation/results in the same transaction as their deletion or
use an equally strong original-result mechanism. A connection/COMMIT interruption
is `unknown` until that original result is verified. No automatic destructive retry.
Trusted Python values are internal composition, not an authentication boundary.

The JSON codecs are strict UTF-8 (no BOM), reject duplicate/extra keys and keep
exact input bytes. Request fields are exactly:

- `protocol`: `CLEANUP@1.0`.
- `operation_id`, `invocation_id`: stable original identifiers.
- `subject_digest`, `registry_digest`, `entry_digest`: lowercase SHA256 hex.
- `target`: slash-delimited registry ID, e.g. `business/memory-authoritative`.
- `domain_scope`: nonempty canonical storage scope, private and never logged.
- `selection`: one of the following closed shapes.

| kind | Additional fields | Meaning |
|---|---|---|
| `account` | none | All private records for this canonical domain scope, after account revocation and task-stop barriers. |
| `memory` | `item_id`, `item_version`, `scope_epoch` | Owner verifies the exact current/revoked item under the canonical lock and resolves its sources/candidates/derivatives. Never infer a direct item mapping where none exists. |
| `diagnostics` | `before_unix` | #27 maintenance only: timestamps strictly earlier than the injected-clock 90-day cutoff, only data explicitly classified `diagnostic_90d`. Not a general TTL capability. |

IDs use `[A-Za-z0-9][A-Za-z0-9_.:/-]{0,159}`. Scope is 1–4096 UTF-8
bytes, no NUL. Versions/epochs are integers 1..2^63-1; cutoff is an integer
0..2^63-1 (bool is not int). Request is at most 16384 bytes.

Receipt is at most 4096 bytes and has exactly `protocol`, `request_digest`
(SHA256 of the **exact original request bytes**) and `outcome`, one of
`confirmed`, `unknown`, `failed`. No content, row dump, exception or provider
payload. The coordinator accepts only the original injected owner hook's result,
matching the original request digest; client JSON is never an authoritative receipt.
Same request bytes/receipt bytes are idempotent. A different request on the same
invocation conflicts; confirmed/failed results are immutable. Unknown can resolve
only from the original invocation's actual result.

## Lock, deletion and completion semantics

Account cleanup order is durable account fence/session revocation → stop/settle
in-flight work → domain hooks in FK dependency order → minimal progress projection.
Canonical scope locks serialize fences with all writers. A hook must reject a
wrong scope/subject/version, perform only its registered selection, verify physical
deletion and persist the result before returning `confirmed`. New writers, late
workers and restore/rebuild paths must check the durable fence before publishing.
Removing rows without a fence is insufficient: no hook may recreate an erased
scope. Runtime roles never acquire DELETE, TRUNCATE or role membership.

Memory cleanup first stops use/advances the owner's withdrawal fence, then erases
the exact affected candidate/source/derived records. Keeping original chat is
allowed, but it must not re-enter context by re-extraction. C owns Trip/Draft/Memory
association decisions (including M30's lack of item FK); B does not guess mappings.
Device/file paths and exact keys are resolved and erased by A, not the coordinator.

`confirmed` proves the requested online domain selection was actually erased
with its fence intact. An empty query alone, accepted work, soft deletion,
retrieval exclusion, cancellation, SDK clear, unprovisioned storage or expiry is
not confirmation. On a first empty domain, the owner must establish/verify the
fence and commit the original result before confirming. FK/other-domain failures
are explicit failed/unknown; no success default or cascade into unregistered data.

Progress distinguishes `blocked`, `unknown`, `failed`, `in_progress`, `complete`.
Online completion requires every applicable frozen target's actual receipt and
a current registry audit. Backup (30-day rolling, #30), offline device (14 days
from last successful sync, #24/#29) and external retention remain separately
visible unresolved obligations. Do not translate online completion to instantaneous
erasure of all backups/devices or reuse it as the old rc aggregate `complete`.
Only a separately verified full set can produce whole-operation `complete`.

Post-revocation access is limited to an authenticated query of that same original
operation's whitelisted progress; it grants no ordinary domain read/write, new
operation, execute or recovery permission. #27 supplies that enforcement and API;
this hook ABI itself supplies no token, route or account access policy.

## Retention and rollback

See [shared design](DESIGN.md). User content remains until explicit user deletion
or account deletion. Diagnostic retention is 90 days; account-linked usage ledger,
reservation/unknown settlement and action receipts are reconciliation/billing
evidence, **not runtime logs**, and are not shortened by diagnostics maintenance.
No compliance exception preserving identifiable account data is assumed.

Only additive local migrations, with explicit table/role ACLs and forced RLS.
Empty-database down/up is verified; down refuses nonempty new state. Revoking
role grants disables further deletion; reverting code cannot restore deleted data.
Never restore a backup without replaying fences before sensitive reads/writes.

Examples: [positive](examples/v1-positive.json), [negative](examples/v1-negative.json).
`backend/cleanup/tests/test_hooks.py` exercises both and binding/strict-codec failures.
