# FEASIBILITY@1.0

Frozen by C under JT's 2026-10-30 standing authorization. This is an additive
trusted-host Python contract; old candidate versions and their byte semantics
remain unchanged. It grants no write, auth, provider or publication authority.

## Shared core

```python
from cj_feasibility.v1 import check_constraints, check_edit_scope, solve_constraints

checked = check_constraints(authorized_snapshot, exact_revisions)
protected = check_edit_scope(before, before_revisions, candidate,
    selected_fields=explicit_fields, selected_item_ids=explicit_item_ids)
solved = solve_constraints(problem, limits, stop=explicit_stop_event)
```

All return immutable `Result(operation, report)` with `version='FEASIBILITY@1.0'`
and `input_profile='CJ-FEASIBILITY-PINNED-CANDIDATES@1'`. `operation` is `check`,
`protect` or `solve`; `status` is the unchanged underlying report status. The
original report, original source bytes, input version, missing evidence, bilingual
explanations and independently checked candidate remain available in `report`.
No hash, caller-supplied DTO or constructed Result proves ownership/currentness.
Only a host's canonical protected read/lease can authorize input and publication.
Do not expose these private objects outside that lifetime or log original text.

This first profile consumes the actual existing NEEDS Snapshot/Revision/Candidate,
PLACE RouteAssessment and solver Problem/Limits types already documented in
README/ROUTES/SOLVER. It delegates to the accepted `evaluate`, `protect`, `solve`
and independent `output_check`; it adds no alternative priority/version/constraint
engine. Existing domain versions stay exactly as emitted before. The facade does
not claim NEEDS@1.0 or PLACE@1.0 has frozen. Their formal-owner producer bridge,
actual route evidence, current source lease and runtime activation are #281.

## Conclusions and protection

| Operation | Status | Meaning |
|---|---|---|
| check/protect | INVALID | Input, source chain or candidate association invalid |
| check/protect | CONFLICT | A specific declared constraint/protected-scope counterexample |
| check/protect | UNKNOWN | Full feasibility unproved; inspect each check, never infer global PASS |
| solve | CONDITIONAL_SOLUTION | Explicit supplied constraints met by independently checked candidate; overall UNKNOWN |
| solve | CONDITIONAL_UNSAT | Native proof for these exact supplied constraints; no real-world infeasibility claim |
| solve | TIMEOUT | Preparation/model/search/output budget exhausted; no unsat proof or candidate publication |
| solve | UNKNOWN | Missing/inapplicable evidence, cancellation, unsupported input or failure; no candidate |

Checks retain PASS/CONFLICT/UNKNOWN/INVALID/NOT_APPLICABLE and both `zh`/`en` from
the same decision. A sole `PROTECTED_SCOPE_UNCHANGED/PASS` is a local equality
check, never permission to save. Locked and unselected originals stay equal; an
unknown lock cannot be guessed unlocked. Expanding selection requires new user
review. The proposed bytes cannot borrow committed source history.

Time remains explicit date/time/IANA zone with unique UTC round trips; DST fold,
gap, missing date or zone is visible UNKNOWN. The original half-open occupancy
rules apply. Routes require original request/source/time/endpoint applicability,
actual duration plus explicit buffer and rest. Missing or stale quantities are
not zero. A 60-minute route cannot fit a fixed 15-minute gap. No departure-time
extrapolation, provider query or travel identity is invented.

Budgets retain exact Decimal/rational arithmetic, currency, total/per-person,
party and scope evidence. No inferred FX, coverage, paid-status subtraction or
zero prices. Arithmetic relations do not certify equivalent caps or real costs;
incomplete money meaning remains UNKNOWN. Formal #281 integration must preserve
those distinctions when the upstream owners freeze the necessary fields.

Limits are the existing explicit Limits (no default horizon, search time, scale,
conflicts, items, edges or revisions). CP-SAT runs bounded with one search worker;
independent verification reads original/output objects rather than native solver
status/variables. #176's startup import policy stays unchanged. Consumers requiring
an OS-level time/memory kill must arrange it explicitly; this API is phase-budgeted.
