# SERVICE-REQUEST@1

真人服务请求的契约（#1768，W9-1，总票 #1714）。依据：ADR-0010；ADR-0005 第 10、11 条与 ADR-0009 第 3、4、6 条的 2026-11-26 修订；PIPIA 增补 `docs/privacy/pipia-service-request.md`（第 11 节决定）。

本版只有一个服务类型：`gz_business_escort_zh_en`（广州中英商务陪同）。构建 58 **App 内不付款**：报价后由人工给出外部支付方式，线下核对。本契约不含支付凭据、支付链接、APNs。

可执行校验：`backend/service_request/cj_service_request/contract.py`；正负例：[examples/v1-positive.json](examples/v1-positive.json)、[examples/v1-negative.json](examples/v1-negative.json)；测试：`backend/tests/test_service_request_contract.py`。

## 1. 开关

- 服务端开关 `CJ_SERVICE_REQUEST_ENABLED`，**默认关**（未设置或不是 `1` 都算关）。只有内部账号名单内的账号在开关打开时能提交。
- 开关关闭时：新提交一律 `404 feature_disabled`，不写库；**已有请求仍可读回**；用户仍可取消未结束的请求；运营台仍可把已有请求推进到结束状态（完成、无法提供、结果未知）。关开关不删除、不改写任何已有记录。

## 2. 状态

| 值 | 含义 | 谁进入 |
|---|---|---|
| `draft` | 草稿，只在客户端 | 客户端 |
| `user_confirmed` | 用户在确认页核对并分项勾选同意 | 用户（随提交一并记录） |
| `submitted` | 服务端已收下 | 系统 |
| `accepted` | 人工已接收 | 员工 |
| `quoted` | 已报价（App 外支付） | 员工 |
| `arranged` | 已安排陪同，双方确认 | 员工 |
| `in_progress` | 陪同已到场，服务进行中 | 员工 |
| `completed` | 已完成 | 员工 |
| `user_cancelled` | 用户取消 | 用户 / 员工代用户登记 |
| `unavailable` | 无法提供 | 员工 |
| `outcome_unknown` | 结果未知（不能确认是否完成） | 员工 / 系统 |

`draft` 不上传服务端。提交时服务端在同一事务内写两条历史：`user_confirmed`（凭据为同意记录）和 `submitted`。

结束状态：`completed`、`user_cancelled`、`unavailable`、`outcome_unknown`。结束后不能再变，`outcome_unknown` 可由员工凭证据改为 `completed` 或 `unavailable`（唯一例外，历史保留原条目）。改判后，保留期和陪同可见窗口都从**首次进入结束状态**的时间起算，不重新起算。

允许的转换（其余一律 `409 invalid_transition`）：

| 从 | 到 |
|---|---|
| `submitted` | `accepted`、`unavailable`、`user_cancelled` |
| `accepted` | `quoted`、`unavailable`、`user_cancelled` |
| `quoted` | `quoted`（改价，须新凭据）、`arranged`、`unavailable`、`user_cancelled` |
| `arranged` | `in_progress`、`unavailable`、`user_cancelled`、`outcome_unknown` |
| `in_progress` | `completed`、`outcome_unknown` |
| `outcome_unknown` | `completed`、`unavailable` |

用户只能做 `→ user_cancelled`；其余转换只能由员工或系统做，其中 `→ completed` 只能由员工做。**不得把未知显示成成功**：员工拿不到完成凭据时只能记 `outcome_unknown`。

## 3. 状态历史与凭据

每次状态变化追加一条，不改不删（随保留期和注销整体清理）：

```json
{"seq": 3, "from": "accepted", "to": "quoted", "at": "2026-12-02T03:00:00Z",
 "actor": {"kind": "staff"}, "evidence": {"kind": "quote", "ref": "ev_..."}}
```

- `actor.kind`：`user` | `staff` | `system`。员工内部标识只存服务端审计，**不进对客字段**（ADR-0009 第 3 条修订）。
- `evidence.kind` 与目标状态对应，缺凭据的转换拒绝（`400 evidence_required`）：

| 目标状态 | evidence.kind |
|---|---|
| `user_confirmed` | `consent` |
| `submitted` | `receipt` |
| `accepted` | `staff_accept` |
| `quoted` | `quote` |
| `arranged` | `arrangement`（陪同已确认可到场） |
| `in_progress` | `arrival` |
| `completed` | `completion_summary`（一句话纪要，见第 7 节保留期） |
| `user_cancelled` | `cancellation` |
| `unavailable` | `unavailable_reason` |
| `outcome_unknown` | `unknown_reason` |

凭据正文（纪要、原因）只给运营台；对客只给状态和下面第 5 节的字段。

## 4. 提交与幂等

`POST /v1/service-requests`，`Authorization: Bearer <access token>`，正文为原始 UTF-8 JSON，键必须正好是：

| 字段 | 规则 |
|---|---|
| `client_request_id` | `[A-Za-z0-9_-]{1,128}`，首次请求前生成并保存 |
| `service_type` | 只能 `gz_business_escort_zh_en` |
| `service_date` | `YYYY-MM-DD`，广州当地日期 |
| `time_window` | `half_day_am` \| `half_day_pm` \| `full_day` |
| `venue` | 会面地点（展馆 / 写字楼 / 工厂地址），非空，≤200 字符 |
| `customer_name` | 陪同怎么称呼客户，非空，≤40 字符 |
| `contact_phone` | E.164 电话号码（`+` 加 8–15 位数字）；现场联系只用电话 |
| `meeting_purpose` | 可空字符串，≤300 字符 |
| `counterpart` | `null`，或 `{"company": ≤80, "name": ≤40}`（只填称呼和公司名，两项都可空字符串但不能都空） |
| `note` | 可空字符串，≤500 字符；不转给陪同 |
| `consents` | 正好三个键 `location_sensitive`、`share_with_escort`、`cross_border`，值都必须是 `true`；加 `text_version`（确认页文案版本，`[A-Za-z0-9._-]{1,32}`） |

日期须为真实存在的日历日；电话和日期只接受 ASCII 数字。文本字段不得含孤立代理字符；必填文本去掉空白和零宽字符后不能为空。整体 ≤8192 字节。多余或重复的键、错误 Unicode、NUL、预勾选以外的任何同意值（`false`、缺项）都 `400`。调用方不能传 `owner`、`state`、`quote`、员工字段。

幂等：同账号同 `client_request_id` 且原文字节相同 → 返回原来的请求（`200`，不新建）；字节不同 → `409 conflict`。不确定是否提交成功时，用同一 ID 和原文重发，或 `GET /v1/service-requests?client_request_id=<ID>` 读回（不存在返回 `request: null`，不代表可以换新 ID）。

## 5. 读回与对客字段

`GET /v1/service-requests/<request_id>` 与列表 `GET /v1/service-requests` 只返回本人的请求；他人的与不存在的不可区分（`404`）。响应：

```json
{"request_id": "sr_...", "client_request_id": "...", "service_type": "gz_business_escort_zh_en",
 "state": "arranged", "history": [{"seq":1,"to":"user_confirmed","actor":{"kind":"user"},"at":"..."}],
 "details": {"service_date": "...", "time_window": "...", "venue": "...", "customer_name": "...",
             "contact_phone": "...", "meeting_purpose": "...", "counterpart": null, "note": ""},
 "shared_with_escort": ["customer_name", "language", "service_date", "time_window", "venue", "contact_phone"],
 "human_service": {...}, "quote": {...}}
```

- 对客历史只含 `seq/from/to/at/actor.kind`，不含凭据正文和员工标识。
- **`shared_with_escort`**：按本次授权列出将与陪同共享的字段，服务端按用户实际填写计算（`language` 不是提交字段，由 `service_type` 推出，本版恒为中英）；只能取自 `customer_name`、`language`、`service_date`、`time_window`、`venue`、`meeting_purpose`、`counterpart`、`contact_phone`。**永不共享**：账号 ID、邮箱、`note`、报价与支付、评价、对话全文、行程、记忆、证件。`meeting_purpose` 为空或 `counterpart` 为 `null` 时不列出。
- **`human_service`**（真人说明，ADR-0005 第 10 条修订；提交起就有）：

| 字段 | 内容 |
|---|---|
| `provided_by_human` | 恒为 `true` |
| `escort_display_name` | 陪同称呼；`arranged` 之前为 `null` |
| `arrival` | `null` 或 `{"local_time": "YYYY-MM-DDTHH:MM", "place": ≤200}`；`arranged` 起必填 |
| `cancellation_policy` | `{"text_en", "text_zh"}`，取消规则原文（由运营给定，版本化） |
| `refund_by` | `{"text_en", "text_zh"}`，写明由谁退款（58 为运营主体人工退款，App 内不退款） |

- **`quote`**：`quoted` 之前为 `null`；之后 `{"amount_minor": 整数分, "currency": "CNY", "payment": "outside_app", "instructions_en", "instructions_zh"}`。58 不给支付链接，只说明「工作人员会告知 App 外的付款方式」。报价对陪同不可见。

## 6. 取消

`POST /v1/service-requests/<request_id>/cancel`，正文 `{"client_request_id": "..."}`（幂等：已是 `user_cancelled` 时返回原结果）。只在非结束状态可用；结束状态 `409 invalid_transition`。开关关闭时照常可用。

## 7. 陪同可见、保留与清理

- 陪同可见 `shared_with_escort` 列出的字段，窗口从进入 `arranged` 起，到服务结束（进入结束状态）后 24 小时止；每次查看留审计。
- 保留：请求、状态历史、凭据在进入结束状态后 12 个月删除；`completion_summary` 正文 90 天删除；用户可提前删除结束的请求。
- 注销：账号清理钩子删除该账号全部服务请求、历史、凭据和陪同查看审计中可关联到用户的明文，fail-closed，挡住清理后迟到的写入（W9-2 实现并登记 `backend/storage-registry.json`）。
- 服务请求和纪要不进长期记忆、不进行程规划上下文。

## 8. 错误

`401` 无效凭证；`400 invalid_input` / `evidence_required`；`404 feature_disabled`（仅新提交）/ `not_found`；`409 conflict` / `invalid_transition`；`413` 超长；`415` 媒体类型；`503` 存储或鉴权不可用（写入结果不确定时 `outcome: unknown, recovery: reconcile_original`）。错误和日志里不出现请求正文、电话、地址。

## 9. 不在本版

App 内付款与真实收款（59A）；推送；多城市、多服务类型；陪同端 App；官网接单入口的表单（#1777，复用本契约的提交字段，另需 PIPIA 扩展）。
