# Lio 用户版 UI/UX 重设计规划（供实现会话使用）

状态：**JT 已于 2026-11-11 同意 D1–D5 全部五项**（见[第 6 节](#6-需要-jt-决定的规格变更)）。本文只做规划，不改代码。[docs/ui.md](../ui.md)「Lio 用户版」尚未同步这五项，由各实现 PR 在落地对应改动时一并更新。

范围：`ios/Modules/CJShell/Sources/CJLioUser/**`、`CJShell/LioSavedMemoryView.swift`、`ios/App` 中的 `LioMenuSettings`。Debug 用的 CJShell 页面不动。

## 1. 现状诊断

读的是 `LioHome.swift`、`LioTripsView.swift`、`LioInvitationView.swift`、`LioSavedMemoryView.swift`、`LioReplyMarkdown.swift`。

| 位置 | 现状 | 问题 |
|---|---|---|
| 全局 | 没有任何设计 token；颜色全是 `systemBackground` / `secondarySystemBackground` / 默认蓝色 `accentColor`；圆角 7/16/20/27 散落各处 | 看起来是系统默认样式，没有品牌感；醒狮头像的红、翠绿、金、米白完全没用上 |
| 顶部 | 菜单按钮是文字字符「≋」；头像＋名字胶囊居中 | 字符不是图标，粗细和基线与系统不一致 |
| 首屏 | 一条开场气泡＋四条等宽灰色长条示例 | 首屏是整个 App 的第一印象，目前像一张表单；四条示例没有类别区分 |
| Lio 回答 | 整段 Markdown 塞在一个灰色气泡里，右侧留 22pt | 长回答（标题、列表、行程说明）在气泡里很挤，可读宽度被浪费 |
| 等待 | 一行脚注「Lio 正在回复…」＋脉冲图标 | 位置在问题下方、没有头像，感觉不到是 Lio 在回应 |
| 输入框 | 灰色胶囊，发送键黑色圆形，底部一整条不透明背景 | 和内容之间有硬边；发送键没有品牌色 |
| 行程卡 | 灰底卡片＋系统 `DisclosureGroup`＋「已保存到行程 · 查看」按钮 | 这是产品的核心产出，目前和一条普通气泡同级，看不出「这是一份行程」 |
| 记忆确认 | 灰底卡片＋蓝色大按钮；结果「已记住」显示在消息列表最底部 | 结果提示和触发它的那条回答分离 |
| 行程 Tab | `insetGrouped` 列表，每行只有标题；详情是纯文字时间线，地图要点按钮才开 | 没有日期、天数、地点等摘要；地图和时间线割裂 |
| 记忆 Tab | 纯文本列表 | 空状态和列表都没有引导 |
| 邀请码页 | 系统 `Form` | 第一次打开看到的是设置页样式 |
| 交互 | 用户上滑后没有「回到最新」；消息没有长按操作；没有触感反馈 | 都是 AI 聊天 App 的基础预期 |

## 2. 竞品调研与提取的元素

说明：公开资料对各 App 当前版本界面的描述很少。下表「来源」列标 **检索** 的是本次查到的页面，标 **经验** 的来自对这些 App 截至 2026 年中的了解，未逐一核对最新版本，实现前如有疑问应以真机截图为准。

| 产品 | 观察到的做法 | 来源 | 用到 Lio 的地方 |
|---|---|---|---|
| ChatGPT / Claude / Gemini iOS | 助手回答不套气泡，直接铺在页面上；只有用户消息是气泡 | 经验 | 3.3 回答排版 |
| 同上 | 输入框悬浮在内容上方，内容从下面滚过；流式时发送键变停止键 | 经验 | 3.4 输入框 |
| 同上 | 首屏是问候语＋几张可点的建议卡，而不是聊天记录 | 经验 | 3.2 首屏 |
| Claude iOS | 暖色纸张底色＋衬线字体做问候语，区别于冷白底的工具感 | 经验；[Liquid Glass 改版报道](https://cryptobriefing.com/claude-liquid-glass-ios-redesign/)（检索，单一来源） | 3.1 色彩与字体 |
| Pi（Inflection / ustwo） | 目标是「calm, curious, human」，主动去掉常见 UI 惯例；「Discover」引导开启话题 | [ustwo 案例](https://ustwo.com/work/inflection-ai/)（检索） | 整体克制；首屏建议卡 |
| Mindtrip iOS | 回答里嵌入地点卡（图、评分、标题）；行程与聊天并存，可在看行程时收起对话；主页 Tab＋行程 Tab | [App Store 页面](https://apps.apple.com/app/mindtrip-ai-travel-companion/id6503107567)（检索） | 3.5 行程卡；3.7 行程 Tab |
| Mindtrip / Trip.com / ChatGPT 对比评测 | 纯文字行程被评为「原始」；地图要能看出节奏而不只是路线 | [Afar 评测](https://www.afar.com/magazine/we-tested-ai-travel-planning-apps-here-are-the-3-that-actually-worked)（检索） | 3.5、3.7 |
| Amadeus UX 研究 | 「探索用对话，意图明确后用确定性 UI」；1,031 人调查中 70% 接受带交互元素的聊天，66% 接受纯文字；引用的 Google 研究里生成式 UI 对纯文本的两两偏好为 97% | [Amadeus 工程博客](https://amadeus.com/en/engineering-blog/articles/ai-chatbot-travel-chat-generated-ui-decisional-ux)（检索） | 行程卡、记忆确认、撤销都做成组件而不是文字 |
| Setproduct 聊天界面指南 | 只在距底部约 100px 内自动跟随，上滑后显示「回到最新」；错误写明原因和一个恢复动作；避免圆滚滚的短信式气泡；消息操作在移动端常驻 | [Setproduct](https://www.setproduct.com/blog/ai-chat-interface-ui-design)（检索） | 3.3、3.9 |
| iOS 26 Liquid Glass | 玻璃只用在导航和控件层，不用在内容上；多个玻璃元素放进同一个容器；需要 `#available` 回退 | [第三方总结](https://dev.to/diskcleankit/liquid-glass-in-swift-official-best-practices-for-ios-26-macos-tahoe-1coo)（检索，非 Apple 官方文档） | 3.4、3.10 |
| 豆包 / 元宝 / Kimi | 检索只查到市场数据，没有界面分析 | — | 未采用 |

三条设计结论：

1. **Lio 要有自己的样子。** 头像已经给出了配色：朱红、翠绿、金、米白。把它变成一套克制的 token，而不是把界面刷红。
2. **回答是内容，不是短信。** 用户消息保留气泡，Lio 的回答铺开排版；行程、记忆确认这些「结果」做成有明确形态的卡片。
3. **行程是持久对象，聊天是修改它的方式。** 行程卡和行程 Tab 要像同一个东西的两种视图，地图与时间线放在一起。

## 3. 设计方案

### 3.1 设计 token（新增 `LioTheme.swift` ＋ `LioAssets.xcassets` 颜色集）

颜色全部进 asset catalog，带浅色/深色两套；代码里只引用语义名。下面的色值是起点，实现时需用对比度检查确认正文 ≥ 4.5:1、大字和图标 ≥ 3:1，不达标就调深浅，不改色相。

| 语义名 | 浅色 | 深色 | 用途 |
|---|---|---|---|
| `paper` | `#FAF6EF` | `#16130F` | 页面底色（聊天、行程、记忆） |
| `surface` | `#FFFFFF` | `#211D18` | 卡片、输入框 |
| `surfaceSunken` | `#F1EADF` | `#2B2620` | 用户气泡、次级填充 |
| `ink` | `#1F1A15` | `#F3EDE4` | 正文 |
| `inkSecondary` | `#6B6157` | `#A89E92` | 次要文字、时间 |
| `hairline` | `#E4DACB` | `#3A332B` | 0.5pt 分隔线和卡片描边 |
| `vermilion` | `#C2362B` | `#E8604F` | 唯一的主操作色：发送键、主按钮、链接 |
| `jade` | `#1E7B5C` | `#4FB893` | 「已保存」「已记住」等成功状态，固定安排的锁 |
| `gold` | `#8A6516` | `#D4AE5C` | 记忆相关的图标和强调 |
| `danger` | 系统 `red` | 系统 `red` | 发送失败 |

规则：一屏里朱红只出现在一个主操作上；翠绿和金只做状态和小图标，不做大面积底色。

字体：

- 正文、按钮、标签：系统字体，全部用 Dynamic Type 文本样式，不写死字号。
- 展示级文字（首屏问候、行程卡标题、Tab 页大标题）：`Font.system(.title2, design: .serif)`。系统的 serif 设计对中文不生效，中文展示文字需单独指定 `Songti SC` 并用 `relativeTo:` 跟随 Dynamic Type。**实现时先在模拟器确认该字体在目标系统可用且粗细合适，不合适就中文回退系统字体，只让英文用衬线。**
- 回答正文行距 `lineSpacing(4)`，段间距保持现有 `\n\n`。

间距 4 / 8 / 12 / 16 / 24 / 32；圆角统一为 12（小卡、芯片）、20（卡片、气泡）、胶囊（输入框、顶部控件）；卡片不用阴影，用 `hairline` 描边区分层次。

动效：出现用 `spring(duration: 0.3)`，状态切换 `easeOut 0.2`；`accessibilityReduceMotion` 开启时全部改为无动画或淡入，沿用现有判断。

│                              │
│ ┌────────────┐┌────────────┐ │

│ └────────────┘└────────────┘ │

- 四个示例文案不变，点选仍然只填草稿；每张卡加 SF Symbol 和类别标签（出行 / 规划行程 / 住宿 / 我的偏好）。
- 辅助功能字号下 2×2 改为单列。
- 保留 `lio.opening`、`lio.example.N` 标识。
- 现行规格要求开场是「普通聊天气泡」且「不设欢迎卡」，所以这一版需要 JT 确认（[第 6 节](#6-需要-jt-决定的规格变更) D1）。未确认时的做法：开场仍是气泡，只把四个示例改成 2×2 卡片。
- 有消息后、以及从后台回来时的开场，仍按现有逻辑显示为一条普通的 Lio 回答。

### 3.3 对话

- **用户消息**：靠右，`surfaceSunken` 底、`ink` 字，圆角 20、右下角 6；最大宽度约为内容区的 80%。
- **Lio 回答**：靠左，不套气泡，占满内容宽度（上限仍 680pt）；每轮回答开头放 22pt 头像＋「Lio」小标签，后面是 Markdown 正文。标题层级沿用 `LioReplyMarkdown` 的输出，只把标题字体换成展示字。需要 JT 确认（D2）。未确认时的做法：保留气泡，底色改 `surface`＋`hairline` 描边，去掉右侧 22pt 留白。
- **等待**：在 Lio 回答的位置显示头像＋三点跳动；`lio.progress` 标识和「Lio 正在回复…」朗读文案保留在同一元素上。正文开始流出后三点消失。
- **失败**：红色感叹号、各类失败文案、「重新问」按钮的逻辑都不变；文案改用 `inkSecondary`，「重新问」用描边按钮。
- **回到最新**：`followsAnswer == false` 时在输入框上方居中显示一个向下箭头的圆形按钮，点按滚到底并恢复跟随。新增标识 `lio.jumpToLatest`。
- **长按消息**：`contextMenu` 提供「复制」。只做这一项；重新生成、分享、点赞不在本次范围。
- **更早的消息**：按钮改为居中的小号文字按钮，加载时在原位显示 `ProgressView`。

### 3.4 顶部控件与输入框

- 菜单按钮：`Image(systemName: "line.3.horizontal")`，44×44 圆形；`lio.menu` 与无障碍标签不变。
- 头像胶囊保持居中。右侧对称位置加「新对话」按钮（`square.and.pencil`），只在 `chatLibrary != nil` 时显示，禁用条件与菜单里的「新对话」相同；菜单里的入口保留。新增标识 `lio.chat.newShortcut`。
- 顶部控件和输入框的背景：iOS 26 及以上用 `glassEffect`，放进同一个 `GlassEffectContainer`；以下版本用 `.regularMaterial`。删除顶部和底部的整条不透明底色，改为内容从控件下方滚过，上下各加一段 `paper → 透明` 的渐隐。**部署目标是 iOS 17，所有玻璃 API 必须包在 `#available(iOS 26, *)` 里，并先确认 CI 的 Xcode 版本能编译这些符号；不能编译就整项推迟，只用 material。**
- 输入框：`surface` 底＋`hairline` 描边的胶囊，最小高度 52；发送键可用时 `vermilion` 底白色箭头，不可用时 `surfaceSunken` 底。占位文案、`lio.composer`、`lio.send` 不变。
- 发送成功触发一次轻触感（`sensoryFeedback(.impact(weight: .light))`）。

停止生成、语音输入、附件都不在本次范围：Lio 外壳目前没有接这些能力。

### 3.5 行程卡（对话内）

```
┌────────────────────────────────┐
│ 🗓 行程                    ✓已保存 │  顶栏：类别标签＋翠绿状态
│ 北京三天两晚                      │  展示字标题
│ 3 天 · 11月20日–22日 · 9 个地点    │  摘要行
│ ─────────────────────────────── │
│ (第1天) (第2天) (第3天)           │  横向日期芯片，选中的那天展开
│  09:00 ● 故宫                    │
│        │                        │  时间轴竖线
│  12:30 ● 四季民福                 │
│  14:00 🔒 酒店大堂 · 固定安排      │
│ ─────────────────────────────── │
│ [ 查看完整行程 → ]      撤销       │
└────────────────────────────────┘
```

- `surface` 底、`hairline` 描边、圆角 20。
- 开头的安排依据说明（`planningIntroduction`）移到卡片上方，作为 Lio 回答正文的一部分，卡片内不再重复。
- 日期用横向芯片切换，默认选第一天；卡内最多显示 4 个地点，超出显示「还有 N 项」并引导到行程 Tab。这替换掉现在的 `DisclosureGroup`，是否算偏离规格里的「按天折叠」见 D3。
- 状态标签：有保存证据才显示「✓ 已保存」（`jade`）；现有「没有保存成功的证据就不显示已保存」的判断逻辑不动。
- 「已保存到行程 · 查看」的文案和 `lio.trip.show` 标识保留在主按钮上；「撤销」`lio.chat.trip.undo` 为次级文字按钮，禁用条件不变。
- 「正在等行程更新…」显示在卡片底部一行，带小号 `ProgressView`。
- `lio.trip.day.N` 标识挂在对应的日期芯片上。**这会改变 UI 测试的交互方式（原来是展开，现在是选择），对应用例需要同步修改。**

### 3.6 记忆确认

- 紧跟相关回答，一行式小卡：金色书签图标＋「记住：……？」＋右侧两个按钮「记住」（`vermilion` 描边）「不用」（文字）。辅助功能字号下按钮换行。
- 点「记住」后，卡片原地变为「✓ 已记住」（`jade`）并在约 2 秒后淡出；「这条建议已有变化」「暂时无法保存你的选择」同样在原地显示。现在这些提示统一放在消息列表底部的 `memoryNotice`，需要把状态改为按 tag 记录。
- `lio.memory.remember`、`lio.memory.dismiss`、`lio.memory.waiting` 保留。

### 3.7 行程 Tab

- 列表：每趟行程一张卡，包含标题（展示字）、日期范围、天数、地点数。`StructuredTripSummary` 目前只用到了 `title` 和 `tripID`；**实现前先看它还有哪些字段，没有的摘要项就不显示，不为此改接口。**
- 详情：顶部固定一块约 220pt 的地图，显示当天所有有坐标的地点并按顺序编号；下面是横向日期芯片＋时间轴列表（样式与行程卡一致）。点时间轴上的地点，地图移到对应标记。没有任何坐标时不显示地图块。现有的 `LioDayMap` sheet 和「在地图上看」按钮随之移除；`recordedMap` 注入的视图继续放在列表里。
- 空状态：头像＋「还没有行程」＋「告诉 Lio 你想去哪儿。」＋主按钮「和 Lio 聊聊」，替换 `ContentUnavailableView` 的默认样式。
- 「此前的安排」入口位置和 `lio.trip.history` 不变，历史页只换配色和字体。
- 页面底色 `paper`，列表用 `scrollContentBackground(.hidden)`。

### 3.8 记忆 Tab、菜单、邀请码页

- 记忆 Tab：每条记忆一张小卡（正文最多三行）；停用的记忆降低不透明度并标「Lio 暂时不用这条记忆」；空状态用头像＋现有文案。编辑、删除、删除记录的流程和标识不变，只换样式。
- 菜单：保持 sheet，改为中等高度可上拉（`presentationDetents([.medium, .large])`）。顺序：新对话、历史对话、语言、外观。演示模式的「仅提供演示回答」改为顶部的一条提示条。
- 邀请码页：去掉 `Form`。居中 96pt 头像、展示字标题「和 Lio 聊聊」、说明文案、一个胶囊形邀请码输入框、主按钮「继续」（`vermilion`）、次级文字按钮「继续使用账号」、底部语言/外观设置。同意页同样改为居中布局，主按钮「同意并继续」。所有文案和 `demo.invite.*`、`lio.invite.back` 标识不变。

### 3.9 无障碍与文案（不变的约束）

- 所有现有 `accessibilityIdentifier` 保留；有变动的只有 3.5 的日期芯片交互，以及本文明确列出的新增标识。
- Dynamic Type 到辅助功能字号都要能用；新增的 2×2、横向芯片、一行式卡片都要有大字号下的纵向布局。
- 不新增任何暴露后台操作或内部状态的文案；每个 PR 的静态文案扫描仍须为 0。
- 用户版仍不展示思考步骤、工具动作、供应商来源标签。
- 头像只按圆形遮罩使用，不重绘、不换色、不生成变体。

### 3.10 不做的事

语音、附件、停止生成、消息重新生成/分享/点赞、地点图片卡、订票入口、小组件、App 图标改版。它们需要新的后端能力或素材，另开票。

## 4. 实现拆分（建议的子票顺序）

每一项对应 1 个 PR，只改 `ios/**`（A 线文件）；涉及规格变更的 PR 同时改 `docs/ui.md`。子票、验收框和证据级别由 JT / Claude 按 ADR-0007 正式开票时确定，下表是建议。

## 5. 给实现会话的注意事项

- 先读 `AGENTS.md` 和 `docs/ui.md`；本文是提案，冲突时以 `docs/ui.md` 和 JT 的决定为准。
- 开工前确认 A 线当前没有开着的 PR 在改同一批文件（`LioHome.swift` 是热点）。
- 只换样式和布局，不改 `LioConversation`、`LioTimelineService`、`LioTripPlan`、记忆客户端里的任何状态机、网络或判断逻辑。
- 本文的色值、字号、尺寸是起点；发现对比度、截断、布局问题时在 token 层调整并在 PR 里说明。
- 没有核实过的三件事，动手前先查：`Songti SC` 在目标系统上的可用性；CI 的 Xcode 是否有 iOS 26 SDK；`StructuredTripSummary` 的可用字段。
