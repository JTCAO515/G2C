# ADR-0010：本地助手与场景包

- 状态：**accepted**（以 JT 批准合并为准；合并前是待批草稿。Claude 起草。产品方向本身已由 JT 2026-11-26 决定，见「JT 决定」）
- 日期：2026-11-26
- Issue：[#1735](https://github.com/JTCAO515/G2C/issues/1735)（W7-1，总票 [#1714](https://github.com/JTCAO515/G2C/issues/1714)）
- 关联：[ADR-0001](0001-product-boundaries.md)（目标人群，由 [#1764](https://github.com/JTCAO515/G2C/issues/1764) 改写）、[ADR-0003](0003-state-and-recovery.md)、[ADR-0005](0005-proactive-fulfillment.md) 与 [ADR-0009](0009-jt-agent-contract-reservation.md)（真人服务口径，由 [#1744](https://github.com/JTCAO515/G2C/issues/1744) 修订）、[ADR-0006](0006-membership-and-memory-retention.md)（第 3 条「人工服务不按次收费」同在 #1744 加修订注记）、[记忆规格](../memory.md)

## 背景

到构建 57，G2C 是「外国人来华自由行的 AI 助手」：一个 Lio、四个 Tab（聊天 / 行程 / 工具 / 我的），工具都是旅游向（打车、回酒店、落地模式、景点预约、点餐、酒店、城际交通、路书等）。

JT 2026-11-26 把产品扩为**外国人在中国办事的本地助手**：旅游、商务、在华就医协助共用一个 Lio。扩展带来三个结构问题：

1. 一句话可能同时含不同性质的任务（「下周到广州参展，空半天想逛逛」）。按用户身份分「旅游用户 / 商务用户」会把这句话拆不开。
2. 商务和就医有各自的知识来源、风险规则和可承诺结果，混在一份提示词和一张工具表里，会拖累已上线的旅游基线（57 的规划保存还没稳定）。
3. 首次出现需要真人到场的服务（广州中英商务陪同）。它的履约方、状态和凭据与第三方平台订单（滴滴、Trip.com、Klook、12306）完全不同。

**仓库现状**（`origin/main` 27388ea7）：没有按领域（旅游 / 商务 / 就医）划分的场景，也没有相关开关。代码里已有的 `Scene`（`backend/cj_api/lio_exploration_policy.py`，取值 exploration / adjustment / today / practical / emergency）和 `scene_prompt`（`backend/cj_api/lio_scene.py`）指的是旅游对话的阶段，不是本 ADR 的场景；对话意图按单一旅游语境识别；会话只有行程聊天一种（ADR-0009 第 4 条只预留了服务会话类型）；没有远程推送。

## JT 决定（2026-11-26）

来源：JT 本地工作区 `strategy/roadmap.md`（不入仓库）第 6 节 2026-11-26 条（JT 对方向稿第 9 节前四条回复「按建议定」）。

1. 产品方向扩为外国人在中国办事的本地助手，旅游、商务、在华就医协助共用一个 Lio。
2. 陪同类具名真人服务事先告知客户有真人参与（是谁、何时到）。（落在 ADR-0005 / ADR-0009 修订，#1744）
3. 陪同按次收费，单列为线下服务，与会员权益分开，走 App 外支付（审核指南 3.1.3(e)）；会员仍走 IAP。（同上）
4. 首个真人服务为广州中英商务陪同（半天 / 全天），自签 3–5 名经背调的兼职，含保险和服务协议。
5. 合规包排到最前，服务请求和健康信息的隐私增补在外部试点前完成。

本 ADR 只把第 1 条落成结构决定；第 2、3 条的条款修订在 #1744，第 4 条的人员与协议由 JT 本人推进（#1775），第 5 条在 #1743、#1745、#1746。

## 决定

### 1. 一个入口，按任务分场景

- 用户只面对一个 Lio。不按用户身份分产品、分入口或分 App。
- Lio 把一句话识别为一组任务（`tasks[]`），每项带所属场景、已知信息、缺失信息。只有缺少会改变结果的信息时才追问，一轮最多问一个（与 2026-11-25 定的一屏回答规则一致）。字段名在对话线的契约 PR 里定（#1738）。
- 场景是任务的属性，不是用户的属性。同一位用户同一天可以有商务和旅游两类任务。
- 命名：本 ADR 的「场景」（旅游、商务、就医协助）与现有的对话阶段 `Scene` 是两回事。#1737、#1738 新增的字段和配置须用能区分的名字（例如 `domain` 或 `scene_pack`），不复用 `Scene`。
- 四个 Tab 不变。场景只在聊天的任务卡、工具页分组、行程首页清单、「我的 → 我的服务」里体现。

### 2. 场景包

每个场景包写清五件事：

| 项 | 含义 |
|---|---|
| 知识来源 | 可引用的事实，每条带来源和核对日期、复核期限 |
| 可用工具 | 从同一张工具注册表（#1724）里选，场景包只引用、不另建工具 |
| 流程模板 | 该场景常见任务的步骤，例如参展准备清单 |
| 风险规则 | 不能说、不能做的事，例如商务不代表用户签约或付款，就医不给诊断和用药建议 |
| 可承诺结果 | 能承诺到哪一步、以什么为凭据 |

- 首批两份：**旅游**（继承 57，58 只做回归和修复）、**商务**（广州、中英）。**在华就医协助**从 59 起，范围以 59 的票为准（#1783–#1788）。
- 先只做两份具体配置，第三份出现真实差异后再抽象，不预先设计通用框架。
- 场景包是配置，不是代码分支。格式由 S 线在 #1737 里定，其余票只读。
- 每个场景、城市、真人入口、收款、就医各自有开关，可单独关闭。**关掉商务开关时，旅游行为必须与 57 一致**；这是 58 的放行条件之一。
- 关掉真人入口后，已提交的请求仍能查询和收尾。

### 3. 两种履约，分开显示

| 履约方 | 例子 | G2C 做什么 | 状态以谁为准 |
|---|---|---|---|
| 第三方平台 | 滴滴、Trip.com、Klook、12306 | 跳转和信息准备；订单、交付、售后由平台负责 | 平台；G2C 不承诺票和房 |
| JT 服务流程（真人） | 广州中英商务陪同 | 整理需求、用户确认共享信息、人工接单、报价、安排、回传 | 履约方（运营台）记录 |

- 「准备完成」和「安排完成」在界面上分开：给出路书或清单是准备完成；陪同人员确认接单、时间地点双方确认后才显示「已安排」。
- 真人服务的状态必须如实：**无法提供**（无供给）和**结果未知**（需人工核实）是正式状态，不能接了单再找人，也不能把未知显示成成功。
- 真人服务的契约、存储、服务会话由服务线落地（SERVICE-REQUEST@1，#1768–#1774），并沿用 ADR-0009 第 3、4、6 条：服务会话与行程会话隔离；状态变化由服务端主动写入助手消息、推进同一会话头；存储与清理钩子在同一个 PR 登记 storage-registry。ADR-0009 第 3 条原文「不暴露人工参与」对具名到场的真人服务不适用，以 #1744 的修订为准。

### 4. 记忆按用途分开

- 用户确认过的通用偏好（饮食禁忌、语言等）可以跨场景复用。
- 商务资料（会面对象、公司、地址、行程目的）按任务使用，任务结束后不进入长期记忆，除非用户明确保存为记忆。
- 健康信息是敏感个人信息：独立存储域、单独同意，不进通用记忆，撤回同意即删除（59，#1786、#1787）。
- 每一类新数据流在隐私政策和 PIPIA 里逐项登记后才对外部用户开放（#1743、#1745、#1746）。

### 5. 不做

- 不按用户身份分 App 或分入口；不为每个场景各做一个 Lio。
- 58 不加独立新工具卡：商务分组只复用出示卡、打车、翻译、地址解析等现有能力。
- 58 不在 App 内付款；真人服务的收款见 #1744 修订与 59A。
- 首期商务不做工厂参访组织、代为谈判、验货、评价供应商资质；就医不做诊断、用药建议和以治疗为目的的跨境医疗。
- 一次只扩一个变量：城市和语言分开开放。

## 取舍

- 按任务分场景比按用户分更贴近真实请求，代价是意图识别更复杂。用 30 道旅游 + 商务混合评测题守住（#1738，首轮走到有效下一步 ≥ 85% 为建议门槛，待 JT 确认数字）。
- 场景包共用 Lio 管线，任何改动都可能影响旅游。用开关隔离加旅游回归控制，而不是拆成独立服务。
- 真人服务把 G2C 从「信息 + 跳转」推到「承诺交付」。只在真人确认后显示「已安排」，并保留无法提供和结果未知两种真实状态，以免承诺超出供给。

## 已确认 / 证据 / 待决 / 推断

- **已确认（JT 2026-11-26）**：「JT 决定」1–5。
- **仓库证据**：见「背景」。
- **待决（不挡本 ADR）**：官网手工接单入口做不做（拆票稿第 8 节第 5 条）；服务状态通知是否补 APNs（#1793）；59 就医的范围细节；Build 60 默认内容；本 ADR 引用的数字门槛（混合题 85%，已写在 #1738 验收框，数字待 JT 确认）。
- **由 Claude 起草、随 JT 批准合并生效**：「决定」第 1–5 节的具体写法。其中第 4 节「商务资料按任务使用、任务结束不进长期记忆（除非用户明确保存）」比现行[记忆规格](../memory.md)更窄，请 JT 明确确认。
- **Claude 推断**：两份场景包足以验证结构，第三份再抽象成本最低。
