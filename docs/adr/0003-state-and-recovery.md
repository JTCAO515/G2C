# ADR-0003：正式状态、恢复与撤回

- 状态：**proposed**（设计约定待契约 owner 固定；用户控制要求已见 ADR-0001）
- 日期：2026-10-21
- owner：BASE/MESSAGE/RUN/TRIP/MEMORY/CLEANUP，见 [CJ-005](https://github.com/JTCAO515/G2C/issues/5)

## 背景与选项

模型、客户端、工作流和检索组件可能重试、晚到或持有旧版本。可选方案：由各组件直接写各自的“正式状态”；或者统一业务写入入口与版本语义。建议后者，避免未确认旅程和已撤回记忆重新生效。

## 提议

PostgreSQL 业务层保存正式消息、旅程、记忆条目、动作回执、授权/版本与撤回依据。Agent 只提出候选，内部记忆索引/摘要是派生物，工作流 checkpoint 是执行资料。客户端缓存是有期限的快照，均不得反向覆盖正式状态。

Proposal 发布后不可原地改内容；接受绑定内容标识与预期旅程版本。归属、状态、版本检查和正式写入在同一事务完成。手动“保存”可作为一次确认，不叠加重复确认。用户采用与事实是否核实是两个维度。

写动作使用稳定幂等标识与可查询回执；未知结果先对账。运行状态、业务提交结果与模型付费 attempt 分开，框架恢复不授权盲重发。记忆纠正/停用/删除形成有效性屏障（fence）：所有上下文入口和晚到写入按最新用户/来源版本校验；停止使用和物理清理分别记录。

## 取舍

需要维护事务、派生关系和撤回状态，不能仅依赖缓存 TTL 或 prompt。但可以清楚解释部分成功、阻止重复写入、保留用户确认边界。已发给外部模型的请求和断网设备不能被即时远程抹除，用户说明需如实表达实际控制范围。

## 验证与替换条件

契约阶段交正常、冲突、重复、未知、撤回与晚到样例，具体字段/schema/事件名尚未定义。CJ-015/019/021/024/025 验证真实事务、库/索引/缓存/checkpoint 与重建；见[契约](../contracts.md)和[记忆](../memory.md)。若选定框架无法满足，替换 adapter 或执行组件；任何替代方案须保持用户隔离、确认与撤回语义，并记录新 ADR。
