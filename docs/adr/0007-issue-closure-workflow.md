# ADR-0007：以关闭 Issue 为中心的交付流程

- 状态：**accepted**（JT 于 2026-10-27 批准第 1–4 条推荐决定；第 5–6 条为落地这四条所需的配套规则；同日 JT 修订第 3 条为 Codex 自审，并新增第 7 条自动续作）
- 日期：2026-10-27
- 依据：main `4beb505`（#150 合并后）的只读审查；未运行 pytest / swift test（UNRUN）
- 修订：[ADR-0004](0004-delivery-flow-and-repo-hygiene.md) 第 6 条的合并与审查条件由本 ADR 第 3 条替代；ADR-0004 其余各条继续有效。
- 关联：[交接](../handoff.json)、[CJ-005 / #5](https://github.com/JTCAO515/G2C/issues/5)、[CJ-026 / #29](https://github.com/JTCAO515/G2C/issues/29)、[CJ-028 / #32](https://github.com/JTCAO515/G2C/issues/32)

## 背景（仓库证据）

10/21–10/27 main 共 418 次提交（241 次非合并），合并 114 个 PR，34 个 Issue 只关闭 2 个，且两个都是决策或验证票。原因可以在仓库里逐条核对：

- **关闭门槛只能在最后满足。** 功能票要求真实服务、真机证据，还要等“I 前置”的其他票真实完成（例：#8、#20 正文“最终验证”）。这些证据又都要 JT 逐项授权，因此功能票在结构上无法提前关闭。
- **票太粗。** 一张票有 8 个以上验收框，没有子票，任何单个 PR 都关不掉它。
- **进度不回写。** 114 个已合并 PR 都没有使用 `Closes #N`，只有 15 个提到过 Issue；P0 票 #8、#11、#20 的评论数都是 0，正文仍写着“开发未开始”。
- **CI 的“绿”不完整。** swift job 只跑根包、CJTripClient、CJRunClient；另外 11 个 iOS 模块约 107 个测试文件从未在 CI 执行。
- **门禁只靠约定。** main 没有分支保护，“CI 绿才合并”无法由平台强制。审查期间仓库是 PRIVATE 免费版，API 返回 403；JT 于 2026-10-27 改回 PUBLIC 后，分支保护已可免费启用（API 返回 404 “Branch not protected”）。
- **状态文档滞后。** 每个 PR 都要同步 handoff 和派工单，造成大量文档提交；#150 合并后，main 上的 HANDOFF 仍写着“待 CI / 审查”。

## 决定

### 1. 证据分级；功能票在 L1 关闭

| 级别 | 含义 | 例 |
|---|---|---|
| L0 | CI 内可重复的测试：单测、契约、mock、FakeProvider | `scripts/test.py`、`swift test` |
| L1 | 本机真实组合：全新私有 PG + 本地 app + FakeProvider 端到端；或 iOS 模拟器跑通 | `scripts/pg_suites.py e2e`、模拟器录得的 PASS 表 |
| L2 | 真实外部服务：DashScope、Supabase OTP / 云数据库、高德等 | `scripts/provider_smoke.py` |
| L3 | 真机、受邀内测、目标网络 | CJ-026 / CJ-029 |

- **功能票（`type:feature`）的关闭标准**：所有能在 L0/L1 证明的验收框都 PASS，并在框后附 PR 或 CI 链接。
- **只能在 L2/L3 证明的框不删除**，原地改写为 `→ L2 #32` 或 `→ L3 #29`，并在 #32（CJ-028）或 #29（CJ-026）里新增对应条目，回链原票。功能票此后不再等这些框。
- **“I 前置”只约束 L2/L3。** 上游票用真实实现还是本地实现，只影响集中验证票；功能票达到 L1 即可关闭。
- 验证与发布票（`type:verification`、`type:release`、`type:decision`）保持原验收标准不变，L2/L3 证据集中在这些票里完成。
- 后续改动让已关闭票的证据失效时，重开原票或新开子票，不在别的 PR 里悄悄补。

### 2. 拆子票，一次只推进一张父票

- 父票保留原文，作为总验收。实际执行单位是 GitHub **子票**（sub-issue），使用 `.github/ISSUE_TEMPLATE/slice.md`：2–6 个验收框、每个框写明证据级别、预计 1–2 个 PR。
- 父票的所有 L0/L1 框都能对应到已关闭的子票时，关闭父票。
- **在制上限**：同一时间只有 1 张父票处于开发中，最多 2 个开着的 PR。剩余子票全部被停点卡住的父票算“挂起”，不占这个名额。
- **队列**：以 [docs/plan/issue-plan.md](../plan/issue-plan.md) 为准（2026-10-27 修订，替代原先“#20 → #8 → #11 → #19 → #10 → #12”的写法），当前位置由 `docs/handoff.json` 的 `nextAction` 维护。
- 继续执行 ADR-0004 第 7 条：P2 期间不铺新领域。

### 3. 审查：Codex 自审，分级把关

> 2026-10-27 JT 修订：审查改由 Codex 完成，Claude 不再是合并前的必经环节，改为按 JT 要求抽查。原“红线 PR 须 Claude 审查”的规定被本节替代。

- **审查者与作者分开。** 审查必须在不继承作者上下文的 Codex 会话里进行（新会话或 Codex 自带的 review 功能），对象是 PR 的精确 head。作者会话不能直接写 APPROVE。
- **合并条件**：CI 全部 job 在精确 head 上全绿；审查者在 PR 评论写 `Review: APPROVE <head SHA>`，并附上逐项核对结果；合并时锁定该 head（`gh pr merge --match-head-commit <SHA>`）。
- **所有 PR 的必查项**：改动只覆盖子票范围；每个验收框都有对应测试或命令；没有删除、跳过或放宽已有测试与 CI；没有秘密、本机路径或日志文件入库；handoff 已更新。
- **红线 PR 的追加必查项**。只要触及下列任一项，就是红线 PR，审查评论必须逐条写明对应检查的结果：
  - `backend/migrations/**` 或表结构：新迁移的 up/down 在空库上往返通过；已应用的迁移文件未被改动；
  - `contracts/**`：已冻结版本未改；新冻结的契约有正负样例；
  - 鉴权、权限、会话（`backend/auth/**`、各领域的 scope / owner 校验）：有跨用户读写被拒绝的负例测试；
  - 签名与密钥（`backend/trip/cj_trip/confirmation.py`、`scripts/dev_auth.py`、密钥加载与轮换）：有篡改、过期、错 key 的负例测试；没有把密钥写进日志或响应；
  - 删除或清理用户数据（`backend/cleanup/**`、记忆撤回、账号注销）：有防复活和误删他人数据的负例测试；
  - 付费、计费、用量上限：有超限拒绝的测试；
  - CI 与门禁本身（`.github/**`、`scripts/test.py`、`scripts/pg_suites.py`）：门禁只增不减；任何排除都有 Issue 链接，并写在 PR 里。
- **审查不通过**：审查者评论 `REQUEST CHANGES`，作者返修，再在新 head 上重新审查。
- **以下情况必须停下来等 JT，Codex 不能自行合并：**
  - 需要使用授权清单外的外部资源，或修改仓库设置、云端配置、密钥；
  - 修改 ADR、`AGENTS.md`、`docs/authorizations/**`，或者放宽、删除已有门禁；
  - 对真实环境的不可逆操作，例如删除真实用户数据、在云数据库上执行迁移；
  - 付费、订阅、商店或任何对外公开的承诺。

### 4. 外部资源按里程碑一次性授权

- 每个里程碑开始时，JT 在 `docs/authorizations/<里程碑>.md` 批准一份清单。每一条都要写明：资源、允许的操作、环境、预算上限、有效期、回滚方法。
- 清单之内的操作，Codex 可以直接执行，并在 PR 里报告实际用量。清单之外的操作，或预计会超出预算，必须先停下来问 JT。
- 清单里不写秘密本身，只写存放位置（例如钥匙串条目名）。
- 当前没有任何已批准的条目（见 [M1 清单](../authorizations/M1.md)）。早先的授权记录（例如百炼测试费用）只作历史，不自动转入清单。
- 待 JT 决定：是否在 main 启用分支保护（公开仓库免费），把 CI 全部 job 设为必需检查。修改仓库设置由 JT 执行或明确授权；启用之前，“CI 全绿才合并”继续由审查者人工核对。

### 5. 进度回写到 Issue（配套规则）

- 一个 PR 只对应一张子票。PR 正文第一行写 `Closes #<子票>`。如果一张子票确实需要两个 PR，第一个 PR 写 `Refs #<子票>` 并注明 `Part 1/2`。
- CI 的 `pr-lint` job 检查 PR 正文是否含有 `(Closes|Fixes|Resolves|Refs) #<数字>`，缺少就失败。
- 合并后，作者会话在子票里勾选对应验收框，附上 PR 链接，并同步父票的勾选状态。
- Issue 是进度的唯一记录。PR 描述记录本次的证据表（PASS / FAIL / UNRUN / UNKNOWN）和实现说明。

### 6. 文档精简（配套规则）

- `docs/dispatch/` 下的现有派工单冻结为历史，不再追加实施记录。新的派工内容写在子票正文里。
- `docs/handoff.json` 每个 PR 只更新 `currentPhase`、`acceptedIssue`、`activeWork`、`blockers`、`nextAction`、`lastUpdated`，以及本 PR 的 `verification` 和 `changedFiles`；其余字段只在决策变化时修改。改完运行 `python3 -B scripts/handoff.py render` 与 `check`。

### 7. Codex 自动续作

- 一张子票合并后，Codex 不等指派，直接按 `nextAction` 和第 2 条的队列取下一张子票。父票的验收框没有对应子票时，Codex 自己按模板拆出子票再继续。
- 每次合并后先确认 main 上的 CI 全绿。main 变红时停止取新票，先在一个 PR 里修复；修不好就 revert 引起问题的合并提交。
- 每关闭一张父票，在该父票下评论一份小结：关闭的子票、转到 L2/L3 的框、新开的 Issue、遗留风险。
- 停点分两级（2026-10-27 修订，细则见 [docs/plan/issue-plan.md](../plan/issue-plan.md)“停点与跳过”）：
  - **子票级**：只卡住一张子票（文案或产品决策、owner 为 Claude 且未关闭、前置子票未关闭、连续 3 轮审查未通过）。在子票评论阻塞原因后跳过，继续队列。
  - **仓库级**：第 3 条停点清单中其余各项（授权清单外的外部资源、仓库设置或密钥、ADR 与授权文件、门禁放宽、不可逆操作、付费与对外承诺、main 红且一个 PR 修不好）。停止整个会话。
- 队列做完，或者碰到仓库级停点，就停止并在 handoff 里写明原因。M1 队列以外的票，没有 JT 指派不开工。
