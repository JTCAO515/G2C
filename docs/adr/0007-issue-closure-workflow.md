## 背景（仓库证据）

10/21–10/27 main 共 418 次提交（241 次非合并），合并 114 个 PR，34 个 Issue 只关闭 2 个，且两个都是决策或验证票。原因可以在仓库里逐条核对：

- **关闭门槛只能在最后满足。** 功能票要求真实服务、真机证据，还要等“I 前置”的其他票真实完成（例：#8、#20 正文“最终验证”）。这些证据又都要 JT 逐项授权，因此功能票在结构上无法提前关闭。
- **票太粗。** 一张票有 8 个以上验收框，没有子票，任何单个 PR 都关不掉它。
- **进度不回写。** 114 个已合并 PR 都没有使用 `Closes #N`，只有 15 个提到过 Issue；P0 票 #8、#11、#20 的评论数都是 0，正文仍写着“开发未开始”。
- **CI 的“绿”不完整。** swift job 只跑根包、CJTripClient、CJRunClient；另外 11 个 iOS 模块约 107 个测试文件从未在 CI 执行。
- **门禁只靠约定。** main 没有分支保护，“CI 绿才合并”无法由平台强制。审查期间仓库是 PRIVATE 免费版，API 返回 403；JT 于 2026-10-27 改回 PUBLIC 后，分支保护已可免费启用（API 返回 404 “Branch not protected”）。
- **状态文档滞后。** 每个 PR 都要同步 handoff 和派工单，造成大量文档提交；#150 合并后，main 上的 HANDOFF 仍写着“待 CI / 审查”。

## 决定

### 1. 证据分级；功能票在 L1 关闭

| 级别 | 含义 | 例 |
|---|---|---|
| L0 | CI 内可重复的测试：单测、契约、mock、FakeProvider | `scripts/test.py`、`swift test` |
| L1 | 本机真实组合：全新私有 PG + 本地 app + FakeProvider 端到端；或 iOS 模拟器跑通 | `scripts/pg_suites.py e2e`、模拟器录得的 PASS 表 |
| L2 | 真实外部服务：DashScope、Supabase OTP / 云数据库、高德等 | `scripts/provider_smoke.py` |
| L3 | 真机、受邀内测、目标网络 | CJ-026 / CJ-029 |

- **功能票（`type:feature`）的关闭标准**：所有能在 L0/L1 证明的验收框都 PASS，并在框后附 PR 或 CI 链接。
- **只能在 L2/L3 证明的框不删除**，原地改写为 `→ L2 #32` 或 `→ L3 #29`，并在 #32（CJ-028）或 #29（CJ-026）里新增对应条目，回链原票。功能票此后不再等这些框。
- **“I 前置”只约束 L2/L3。** 上游票用真实实现还是本地实现，只影响集中验证票；功能票达到 L1 即可关闭。
- 验证与发布票（`type:verification`、`type:release`、`type:decision`）保持原验收标准不变，L2/L3 证据集中在这些票里完成。
- 后续改动让已关闭票的证据失效时，重开原票或新开子票，不在别的 PR 里悄悄补。

### 2. 拆子票、按线推进与停点（JT 修订，2026-10-30）

- 父票保留原文作为总验收。子票使用 `.github/ISSUE_TEMPLATE/slice.md`，2–6 个验收框，每框标明 L0–L3；父票的全部 L0/L1 框对应已关闭子票后才关闭。
- 最多 3 条并行线，每条线一个会话、同一时间 1 张父票、最多 1 个开着的 PR。剩余框全被前置卡住的父票挂起、不占名额。线与队列以 [issue-plan](../plan/issue-plan.md) 为准；未被 JT 指派的工作不自行扩展。
- 只改本线拥有的文件；共享文件按文件加锁，清单及分组见 issue-plan。开 PR 前用 `gh pr list`，对每个 OPEN PR 跑 `gh pr diff --name-only` 检查占用。协调文件无同文件冲突即可修改，在 PR 正文写明范围，不等别线确认。
- 拆子票和修改 issue-plan 可直接做，与本线 handoff 合在一个文档 PR。设计写在 PR 正文或票评论，写完继续本线获准实现，不另设设计审批。
- **预授权，不停下来等 JT：**
  - 本线拥有的新契约版本自行冻结，仅新增版本号、不改旧版本；PR 附正负例，在消费方票留言通知后继续，不等回执。
  - 追加式迁移仅用于本地运行时，文件头写明 `local runtime only`。私有 PG 空库 up/down 往返、有数据时 down 拒绝、跨 owner 负例全部通过后可按第 3 条合并。
  - 新表给 `cj_m1_runtime` 授最小 `SELECT`、`INSERT` 及业务需要的列级 `UPDATE`；禁止 `DELETE`/`TRUNCATE`、新角色、`BYPASSRLS`、`SECURITY DEFINER`。
- **只有以下情况停下来问 JT：**
  - 密钥、账号、私钥；
  - 真实外部 API、真实模型（`--real`）或任何费用；
  - 云端、Supabase、生产环境；
  - 修改已应用的迁移或已冻结的契约版本；
  - 删除、跳过或放宽现有测试和 CI；
  - 破坏性数据操作。
- #194、#159 文案待确认直接跳过，不算整线停点。其他阻塞在票上记一行，跳到本线队列下一项，不结束 goal；不等待别线回执。只有整线无可推进项时记录整线阻塞。
- 合并前基于最新 main，禁止 force push；重基后的审查复用条件见第 3 条。P2 期间不铺新领域的原范围约束继续有效。

### 3. 审查与合并（JT 常设授权，2026-10-30）

- **红线 PR**（迁移、RLS/权限、鉴权/会话、签名/密钥、计量出口）：开一个不继承作者上下文的新会话，针对精确 head 做一次独立审查。只有 P0/P1 挡合并；P2 及以下记录到后续 PR 修，不再为其停等 JT。审查评论写明 head、逐项结果及放行结论；无 P0/P1 时写 `Review: APPROVE <head SHA>`，保留较低优先级发现。
- rebase 无冲突，且 PR 改动文件的内容与已审 head 逐字一致时，可沿用原 APPROVE，在 PR 写明原/新 head 与逐文件比对证据；其他情况不得声称原审查覆盖新改动。
- **其他代码 PR**：作者自查清单 + 精确 head CI 全部 job 全绿即可锁 head 合并，不做独立审查。
- **文档、handoff、规划 PR**：精确 head CI 全绿即可锁 head 合并，不做独立审查。
- 所有 PR 保留精确 head CI 门禁，使用 `gh pr merge --match-head-commit <SHA>`；不 force push，不把手写数据、fixture 或旧 head 结果冒充实际验收。P2 放行不改变原票验收标准，也不把 FAIL 改成 PASS。
- 作者自查/红线审查均按实际范围核对：子票范围和文件归属、验收框对应证据、未删跳放宽测试/CI、无秘密/本机路径/日志入库、进度按第 5–6 条记录。
- 红线追加检查按触及范围执行：
  - 新迁移/表：仅追加、`local runtime only`，空库 up/down 往返、有数据 down 拒绝；已应用迁移未改。
  - 新契约：只新增版本，旧冻结版本不变，正负例及消费方通知齐全。
  - RLS/权限/会话：跨 owner 读写负例，最小角色/列权限及当前身份隔离；无上述被禁止权限。
  - 签名/密钥边界：篡改、过期、错 key 负例；无秘密进入日志/响应。实际密钥/账号操作仍按第 2 条停点。
  - 计量出口：实际限额拒绝、未知与原动作恢复；不以通用失败或合成响应代替真实出口证据。
- P0/P1 返修后复审；其他阻塞按第 2 条记停点并推进队列，不额外增加逐项 JT 审批。
- 合并后直接开始下一项，不必等待 main CI 跑完；main 变红时，由造成问题的线立即修复，不宣称未完成的 main CI 已全绿。

### 4. 外部资源按里程碑一次性授权

- 每个里程碑开始时，JT 在 `docs/authorizations/<里程碑>.md` 批准一份清单。每一条都要写明：资源、允许的操作、环境、预算上限、有效期、回滚方法。
- 清单之内的操作，Codex 可以直接执行，并在 PR 里报告实际用量。清单之外的操作，或预计会超出预算，必须先停下来问 JT。
- 清单里不写秘密本身，只写存放位置（例如钥匙串条目名）。
- 当前没有任何已批准的条目（见 [M1 清单](../authorizations/M1.md)）。早先的授权记录（例如百炼测试费用）只作历史，不自动转入清单。
- 待 JT 决定：是否在 main 启用分支保护（公开仓库免费），把 CI 全部 job 设为必需检查。修改仓库设置由 JT 执行或明确授权；启用之前，“CI 全绿才合并”继续由审查者人工核对。

### 5. 进度回写到 Issue（配套规则）

- PR 按一个完整切片交付，不为审查硬拆。功能 PR 对应一张子票；完整关闭写 `Closes #<子票>`，依赖阻塞的部分交付写 `Refs #<子票>` 并说明未交范围，不虚称整票完成。文档修订可用 `Refs #<关联票>`。
- CI 的 `pr-lint` job 检查 PR 正文是否含有 `(Closes|Fixes|Resolves|Refs) #<数字>`，缺少就失败。
- 合并后，作者会话在子票里勾选对应验收框，附上 PR 链接，并同步父票的勾选状态。
- Issue 是进度的唯一记录。票评论只在开 PR、合并、阻塞三个时点写，每次三行以内：head、通过/失败数、未跑检查。新契约对消费票的通知按第 2 条执行，不等待回执。PR 描述保留证据表（PASS / FAIL / UNRUN / UNKNOWN）与实现说明。

### 6. 文档精简（配套规则）

- `docs/dispatch/` 下的现有派工单冻结为历史，不再追加实施记录。新的派工内容写在子票正文里。
- JT 2026-10-30 修订：`docs/handoff.json` 只在 goal 结束或整线阻塞时更新一次，不因单票停点、阶段切换或关闭父票另开 handoff PR。拆子票/issue-plan 的文档修改与本线 handoff 合成一个文档 PR，不另拆仪式。只改本线条目，`nextAction` 分线记录；其他线无需等待 handoff。
- 更新 handoff 时只改 `currentPhase`、`acceptedIssue`、`activeWork`、`blockers`、`nextAction`、`lastUpdated`、`verification` 和 `changedFiles`；其余字段只在决策变化时修改。改完运行 `python3 -B scripts/handoff.py render` 与 `check`。

### 7. Codex 自动续作（JT 修订，2026-10-30）

- 合并后不等指派，按本线队列继续，不必等 main CI 跑完。缺少子票时按模板直接拆分，文件归属与锁保持不变。
- main 变红由造成问题的线立即修复；不得把失败留给别线或把未完成的检查报为 PASS。
- 关闭父票时同步总验收及子票/转 L2/L3 的证据；评论按第 5 条压缩，不新增独立汇报仪式。
- 第 2 条列明的敏感操作停下来问 JT；文案跳过，其他阻塞记一行后跳到本线下一项，不结束 goal、不等别线回执。
- goal 完成或整线阻塞时，按第 6 条更新一次本线 handoff。不能把部分交付或依赖停点标为目标完成。
